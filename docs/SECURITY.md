# Security & child-safety checklist — ZapSavr

This is money, and it belongs to children. Treat every item here as a gate, not a suggestion, before merging anything that touches balances, permissions, or key material.

## Custody boundaries

ZapSavr's own code and any server it runs must never hold a seed phrase, private key, or unscoped credential belonging to a parent's main wallet. The only thing ZapSavr stores about the parent's wallet is the scoped NWC connection details (relay, scoped pubkey, budget), which by design can only do what the parent explicitly allowed. If a feature request would require ZapSavr to hold more than that, that's a signal to redesign the feature, not to add an exception.

The kid's local Cashu balance should be treated as "money a kid can carry in their pocket," bounded to an amount that, if lost or stolen, is a lesson rather than a disaster. Whatever ceiling gets picked, make it a real, enforced number, not an aspiration.

**Named exception, added 2026-08-14: the embedded hot wallet.** `lib/hotwallet-storage.ts` and `lib/hotwallet-sdk.ts` do hold a parent's seed phrase, encrypted at rest — this is the one deliberate, clearly-labeled violation of the paragraph above, opt-in only, never the default, never used by the kid-side app. See `docs/ARCHITECTURE.md`'s "Embedded hot wallet (experimental, opt-in)" for the full reasoning. Two honest limits worth stating plainly here rather than letting them go undocumented:

- **The at-rest encryption is only as strong as the parent's PIN.** The mnemonic is encrypted with AES-GCM, keyed by PBKDF2 (210,000 iterations, SHA-256) over the parent's PIN. A 4-digit PIN has 10,000 possible values — real protection against someone casually opening dev tools and reading `localStorage`, but not against an attacker who has a copy of the ciphertext and time to brute-force it offline. Don't describe this as "secure" without that caveat, and don't reuse this pattern for anything where the threat model needs to survive an offline ciphertext leak.
- **Verified against real (worthless) test infrastructure, not yet against a real payment.** Breez SDK - Spark's `"regtest"` network is a real, shared, Lightspark-hosted network that needs no API key and no self-hosting — see `docs/ARCHITECTURE.md`'s "Embedded hot wallet" for the corrected account (an earlier version of this note wrongly claimed no public testnet existed). Run against it for real: `connect()`, `getInfo()`, `listPayments()`, and generating a real on-chain receive address all succeeded against live infrastructure. Not yet verified: actually receiving funds (Lightspark's regtest faucet has its own bot-detection that blocks automated submission — a human filling in the form by hand is the next step, not something done here), sending a payment on any network, and Lightning at all (regtest has no functioning Lightning network per Breez's own docs, so that only checks out on mainnet with a real API key). Whoever adds a real mainnet key should treat send and Lightning as the first things to verify, not assume they work because the rest connected cleanly.
- **Restore flow, added 2026-08-14, closes a real gap.** The setup screen tells a parent "these 12 words are the only way to recover this wallet," but until this date there was no screen that actually accepted those words back — `isValidMnemonic()` in `lib/hotwallet-sdk.ts` was exported and never called. `screens/HotWallet.tsx`'s `HotWalletSetup` now offers "Restore from a backup phrase instead" on the same intro screen, validating the real BIP39 checksum (not just word count) before encrypting and saving. Covered in `screens/HotWallet.test.tsx`.
- **The PIN protecting this is now rate-limited, added 2026-08-14.** Before this date, `handleUnlockEntry` in `screens/ParentFlow.tsx` had no attempt limiting at all — unlimited guessing against a 4-digit PIN that, as of the same date, also gates a real seed phrase. `lib/storage.ts`'s `recordFailedPinAttempt`/`pinLockedUntil` now introduce a growing delay (10s after 4 wrong tries, 30s after 7, capped at 60s after 10) stored in `localStorage` so it survives closing the tab. Deliberately a **soft** lockout, not a permanent one — it always ends on its own, so a bug here can never lock a parent out of their own funds, which would be worse than the brute-force risk it guards against. Covered in `lib/storage.test.ts`.
- **The "forgot PIN" escape hatch now warns about the hot wallet specifically, added 2026-08-14.** "Forgot it? Disconnect and set up again" clears the family/PIN but deliberately does *not* touch the hot wallet's separate storage key — which means, without a warning, a parent could tap it while holding real hot-wallet funds and silently lose access forever (the mnemonic stays encrypted under the PIN they just forgot; the only way back in is that PIN or the 12-word backup). The button now requires confirmation, and if `hasHotWallet()` is true, the confirmation text says so explicitly before they proceed.
- **A Breez API key is now wired in for mainnet, added 2026-08-15.** See `docs/RUNBOOK.md` for how to actually get and set one, and `docs/ARCHITECTURE.md`'s "Embedded hot wallet" for why this key is deliberately treated as public-safe (rate-limiting, not fund custody) rather than something requiring server-side secrecy — this project has no backend to keep a secret in anyway. Don't let that reasoning quietly get reused for a *different* key later without re-checking it actually has the same "doesn't control funds" property; that property is what makes exposure acceptable here, not client-side embedding in general.
- **"Send to a kid," added 2026-08-15, is scoped to one-tap-with-confirmation on purpose.** Before building it, the question of how far "automate the parent-to-kid payment" should go was put back to the person who asked for it, rather than assumed — recurring/scheduled auto-pay with no per-transfer confirmation was explicitly ruled out for now, because the hot wallet has no NWC-style budget cap the way a kid's own connection does; unattended spending logic without one is a materially bigger risk than a UX shortcut. What shipped: pick a kid, type an amount, confirm — every transfer still requires an explicit parent action, same as every other payment in this app. Demo kids are credited without ever calling the real send function (nothing to actually pay), verified live on regtest; the real-kid path is covered by mocked tests only so far, same honest gap as the rest of the send path above.

## Revocation must always work

A parent revoking the NWC connection from their own wallet must immediately and completely cut off the kid's ability to spend through it, with no dependency on ZapSavr's servers being up, reachable, or even still in business. This is the single most important safety property in the whole system and deserves its own test in the build's test suite, not just a manual check.

**What's actually automated (added 2026-08-13, `app/src/**/*.test.ts{,x}`, run via `npm test` in `app/`, gating every deploy in CI):** the real revocation property above lives in the parent's own wallet, entirely outside this codebase, so it can't be unit-tested here without a live wallet integration test — be honest about that boundary rather than claiming more than the suite covers. What the suite does cover, which is the equivalent property ZapSavr's own code is actually responsible for: `getBalanceSats`/`payInvoice` propagate a dead-or-revoked connection's failure rather than ever swallowing it into a fake success or a stale cached balance (`lib/nwc.test.ts`); `SendPanel` never shows "Paid!" unless the payment call actually resolved (`components/SendPanel.test.tsx`); the parent PIN gate genuinely blocks the family dashboard behind a wrong PIN and only unlocks on the correct one (`screens/ParentFlow.test.tsx`); and `clearState()` revokes the local unlocked session, not just the family data, when a parent disconnects (`lib/storage.test.ts`). Extend this suite, don't let it go stale, whenever one of these paths changes.

## Data minimization

Collect the least amount of data about a child that the app can function with. No behavioral tracking, no ad SDKs, no analytics vendor that builds profiles on minors. If usage analytics are needed for product decisions, keep them aggregate and anonymized, and document exactly what's collected in a place a parent can actually read.

## Key handling on the kid's device

If the kid's app holds any keys at all (a Cashu wallet needs some local key material for proofs), they should be generated and stored using the platform's standard secure storage (Keychain on iOS, Keystore on Android, or the PWA equivalent), never in plain local storage. Losing a phone should be a recoverable event for the parent, not a silent, permanent loss of the kid's savings; design a backup/recovery path (likely tied to the parent's connection) before shipping past the pilot phase.

## Dependency hygiene

Prefer established, audited libraries for anything cryptographic (NWC client, Cashu wallet library, Lightning payment handling). Pin dependency versions, and re-check for known vulnerabilities before each pilot release, not just at project kickoff. This app is a plausible target precisely because it's aimed at a vulnerable population; don't make it an easy one.

**Done 2026-08-14** for the packages that actually touch keys or money: `@breeztech/breez-sdk-spark`, `@scure/bip39`, `@getalby/sdk`, and `light-bolt11-decoder` are pinned to exact versions in `app/package.json` (no `^`), so a routine `npm install` can't silently pull in a newer, unreviewed version of any of them. The rest of the dependency tree (React, Vite, build tooling) still uses caret ranges — that's a deliberate scope choice, not an oversight; re-narrow it if one of those ever starts touching key material directly.

## Client-side attack surface and pipeline integrity

There's no backend here — this is a client-only PWA, which means an XSS anywhere in the app is a direct path to the hot wallet's mnemonic and PIN (both pass through JS memory in plaintext during setup/unlock/send), and the GitHub Actions pipeline that builds and deploys it is the only thing standing between the source code and what a real parent's browser actually runs. `.claude/skills/hotwallet-security-audit/SKILL.md` has the full checklist for auditing this; two findings from the first pass were fixed immediately rather than just logged:

- **Content-Security-Policy, added 2026-08-15** (`app/index.html`). `script-src 'self' 'wasm-unsafe-eval'` (the narrow WASM allowance the hot wallet's Breez SDK needs, not the broader `'unsafe-eval'`), no `'unsafe-inline'` for scripts, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors` deliberately **omitted** rather than included-but-broken — browsers ignore that directive entirely when set via `<meta>` (only an HTTP response header can enforce it), and GitHub Pages' static hosting gives no way to set custom headers, so including it would just be a silent no-op giving false confidence. `connect-src` stays broad (`'self' https: wss:'`) on purpose: the hot wallet and NWC both make real-time calls to third-party Lightning infrastructure whose exact hostnames aren't hardcoded anywhere in this codebase, and guessing wrong would silently break real payments. **Live-verified, not just written and assumed correct:** the first version broke both of `index.html`'s inline anti-FOUC/routing scripts outright (CSP blocks inline `<script>` by design) — found by actually loading the built site and reading the console, not by inspection. Fixed by moving them to `public/theme-init.js` and `public/decode-redirect.js` as external same-origin files, then re-verified clean in a fresh browser tab, including exercising the hot wallet's full WASM-load-and-connect path on regtest under the new policy.
- **Branch protection on `master`, added 2026-08-15.** There was none — no required status check, force-pushes and branch deletion both allowed. Now: `build` (the CI job running lint/test/build) is a required status check for PR merges, force-pushes and deletions are blocked, `enforce_admins` is deliberately left `false` so the solo maintainer's existing direct-push workflow keeps working. Worth being honest about the limit of what this actually buys: required status checks mainly gate PR-based merges, not direct pushes to master (which is how every commit in this project's history has actually landed) — so the real value today is narrower (preventing history rewriting, laying groundwork for if this repo ever gets a second contributor) than "CI now blocks bad commits," which it doesn't, for the workflow actually in use.

## Accessibility

This is a safety issue for this app specifically, not polish: a parent or kid using a screen reader, low vision, or no working camera still needs the parental controls and the payment flows to actually work, not degrade into a feature they're quietly locked out of. Checked and fixed 2026-08-13: every form input has a real, programmatically-associated `<label>` (not just adjacent text — screen readers need the `for`/`id` link, or nothing is announced); focus is visibly indicated on every input, not suppressed; buttons that only used to have an `onClick` on a `<span>` or `<h2>` (the goal rename/target-edit controls) are real `<button>` elements now, reachable and operable by keyboard, not just a mouse; every QR code (the NWC pairing code, a payment request) has a visible, selectable, copyable text fallback next to it, because a QR code is fundamentally a sighted-only, camera-only mechanism otherwise. Text contrast was checked against the actual palette values, not eyeballed — every text/background pair in `src/index.css` clears WCAG AA's 4.5:1 minimum, most well above it. Re-check this list before adding new screens; it's easy to reintroduce an unlabeled input or a QR-only flow without noticing.

## Regulatory awareness

This project sidesteps most of the heaviest child-fintech regulation (COPPA-style rules, e-money licensing) precisely because it's non-custodial and community-run rather than a commercial custodial product. That's a feature of the architecture, not an excuse to stop thinking about it. If this ever grows past a single community pilot into something more public, revisit this assumption explicitly and get real legal input before scaling.

## Before every pilot release, check

Does revocation actually cut off spending immediately, tested end to end. Is the kid-side balance ceiling enforced, not just documented. Are keys on the kid's device in secure storage, not plain text. Has the dependency list been checked for known issues in the last month. Would a parent, reading the data collected, feel comfortable with all of it. Does `npm test` in `app/` still pass, and does it still cover every path a change just touched. Can every screen added since the last release be operated without a mouse and without sight (every input labeled, every QR code has a text fallback)?
